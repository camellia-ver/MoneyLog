## DEF-001 [Critical] `clearToken()` 오타로 로그아웃/세션만료/탈퇴 시 토큰이 삭제되지 않음

### 현상
`MoneyLog/src/main/resources/static/js/auth.js`:
```js
function saveToken(token){
    localStorage.setItem("token", token);
}
function getToken(){
    return localStorage.getItem("token");
}
function clearToken(){
    localStorage.removeItem("toekn");   // 오타: "token"이 아니라 "toekn"
}
function isLoggedIn(){
    return getToken() !== null
}
```
`clearToken()`이 실제로는 존재하지도 않는 `"toekn"` 키를 삭제 시도하기 때문에, 정작 삭제해야 할 `"token"` 키는 그대로 남는다. `clearToken()`은 다음 3곳에서 호출된다.
- `api.js`의 `apiRequest()`: 401 응답 수신 시(세션 만료 처리)
- `profile.js`: 회원 탈퇴 성공 시

### 재현 절차 (Headless Chrome으로 실제 auth.js를 로드하여 실행 — 코드 리뷰가 아닌 실제 실행 결과)
1. `QA/repro_clearToken.html`에서 실제 `auth.js`를 그대로 로드
2. `localStorage.clear()` 후 `saveToken("REAL_JWT_TOKEN_VALUE_ABC123")` 호출
3. `clearToken()` 호출
4. 결과 확인

**실행 결과(headless Chrome 151, `--dump-dom`):**
```json
{
  "1_로그인직후_token값": "REAL_JWT_TOKEN_VALUE_ABC123",
  "2_clearToken호출후_token키값(정상이라면_null이어야함)": "REAL_JWT_TOKEN_VALUE_ABC123",
  "3_clearToken호출후_toekn키값(오타로_생성된_키)": null,
  "4_clearToken호출후_isLoggedIn()": true,
  "5_판정": "FAIL - 토큰이 삭제되지 않음(버그 재현됨)"
}
```

### 2차 재현 (실제 백엔드와 연동된 api.js의 401 처리 경로에서도 동일하게 재현됨)
`QA/repro_api401.html`에서 실제 `api.js`+`auth.js`를 로드하고, 위조된 토큰(`INVALID.TOKEN.VALUE`)으로 실제 로컬 백엔드(`http://localhost:8080/api/categories`)에 요청 → 실제 401 수신 → `apiRequest()` 내부에서 `clearToken()` 호출:
```json
{
  "호출_전_token값": "INVALID.TOKEN.VALUE",
  "401_이후_localStorage_token값(정상이면_null)": "INVALID.TOKEN.VALUE",
  "apiRequest_예외메시지": "인증이 만료되었습니다.",
  "판정": "FAIL - 실제 백엔드 401 응답 후에도 clearToken()이 토큰을 삭제하지 못함(버그 재현)"
}
```

### 영향도
- 세션 만료/로그아웃/탈퇴 후에도 브라우저 localStorage에 유효하지 않은(혹은 탈퇴한 계정의) 토큰이 계속 남아있음
- `dashboard.js`는 `Promise.all([summary, expenses, categories])`로 3개 API를 동시 호출하는데, 토큰이 무효화된 상태에서 이 3개 호출이 각각 401을 받으면 `clearToken()`(실패)+`alert()`+리다이렉트 로직이 **3번 중복 실행**되어 알림창이 3번 뜨는 등 UX가 크게 저하될 수 있음(코드 구조상 유추됨, 실제 alert 중복 여부는 REPO 환경상 시각적 확인 불가로 별도 표기)
- 공용 PC 등에서 "로그아웃"해도 토큰이 남아있어 보안상 바람직하지 않음
- DEF-002(탈퇴 후 잔존 토큰) 시나리오의 직접적 원인이기도 함(탈퇴 시 profile.js가 clearToken()을 호출하지만 실패하므로 토큰이 남음)

### 재현 대상 파일 (본 세션에서 생성, 실제 소스 미변경 — 실제 파일을 복사해 로드만 함)
- `QA/repro_clearToken.html`, `QA/auth_copy.js`(auth.js 원본 그대로 복사)
- `QA/repro_api401.html`, `QA/api_copy.js`(api.js 원본 그대로 복사)

### 제안 수정
`auth.js`의 `clearToken()`에서 `localStorage.removeItem("toekn")` → `localStorage.removeItem("token")`으로 오타 수정.

## DEF-002 [Critical] 회원 탈퇴 후 잔존 토큰으로 API 호출 시 500 오류

### 현상
회원 탈퇴(DELETE /api/users/me) 성공 후, 탈퇴 전 발급된 토큰(만료 전)으로 보호된 API를 호출하면 `UserNotFoundException`이 발생하고 `GlobalExceptionHandler`에서 이를 **500 Internal Server Error**로 매핑한다(다른 NotFound류는 404로 매핑되는 것과 비일관적).

### 재현 절차 (실제 API 호출)
```
1) POST /api/users/signup  {"email":"qa_userC_1786087259@test.local","userName":"QA사용자C","password":"qaPass123"}
   -> 201

2) POST /api/users/login   {"email":"qa_userC_1786087259@test.local","password":"qaPass123"}
   -> 200 {"token":"eyJhbGci...(TOKEN_C)...","userId":29,"expiresIn":3600000}

3) DELETE /api/users/me  (Authorization: Bearer TOKEN_C)  {"password":"qaPass123"}
   -> 204 No Content (탈퇴 성공)

4) GET /api/categories  (Authorization: Bearer TOKEN_C)  <- 탈퇴 전에 발급된, 아직 만료되지 않은 토큰 재사용
   -> 500 Internal Server Error
   {"status":500,"message":"사용자를 찾을 수 없습니다.","timestamp":"2026-08-07T16:21:09.0683371"}
```

### 영향도
- 클라이언트 관점에서는(DEF-001과 결합 시) 탈퇴 후에도 토큰이 남아있으므로, 재방문 시 이 500 오류를 실제로 마주칠 가능성이 있음
- 500은 "서버 오류"로 인식되어 사용자에게 부적절한 메시지를 주고, 서버 로그에 불필요한 ERROR 레벨 스택트레이스를 계속 쌓이게 함
- 실제로 클라이언트가 최종적으로 받는 HTTP 상태는 이 500이 아니라 **DEF-004(전역 401 마스킹 버그)**로 인해 **401**로 관측되는 경우가 있음(경로 및 재현 조건에 따라 다름 - `GET /api/categories` 단순 호출 시엔 본문이 있는 500이 그대로 반환되었으나, 동일 계열의 미처리 예외가 다른 상황(DEF-003)에서는 401로 치환되어 반환됨. 두 현상 모두 "GlobalExceptionHandler가 다루지 않거나 트랜잭션 커밋 이후 발생하는 예외 처리"라는 공통 카테고리에 속함)

### 제안 수정
1. `UserNotFoundException`을 다른 NotFound류와 일관되게 404(또는 세션 관점에서는 401)로 매핑
2. DEF-001을 함께 수정하여애초에 탈퇴 후 토큰이 클라이언트에 남지 않도록 조치

## DEF-003 [Critical, 최우선] 카테고리+지출이 모두 있는 계정은 회원 탈퇴(계정 삭제) 자체가 실패함

### 현상
`User` 엔티티는 `categories`, `expenses` 두 컬렉션에 대해 `cascade = CascadeType.REMOVE`를 선언하고 있으나, `Category`→`Expense`의 관계(`Category.expenses`, `mappedBy="category"`, cascade 없음)와 `Expense.category_id` 컬럼이 `nullable = false`로 선언되어 있어, 회원 탈퇴 시 Hibernate가 `Category`를 삭제하기 전에 연관된 `Expense.category_id`를 `NULL`로 갱신하려 시도하면서 **NOT NULL 제약조건 위반**이 발생한다. 이로 인해 **카테고리와 지출 데이터를 모두 가진 계정은 회원 탈퇴가 전혀 되지 않는다** (실제 서비스에서는 카테고리를 만들고 지출을 등록하는 것이 가장 일반적인 사용 패턴이므로, 사실상 대다수의 실사용 계정에서 탈퇴 기능이 동작하지 않을 것으로 예상됨).

### 재현 절차 (실제 API 호출, 5회 반복하여 100% 재현 확인)
```
1) 회원가입 + 로그인 (userD)
   POST /api/users/signup {"email":"qa_flaky6_...@test.local","userName":"flaky","password":"qaPass123"} -> 201
   POST /api/users/login  -> 200, TOKEN 발급

2) 카테고리 생성
   POST /api/categories (Bearer TOKEN) {"name":"flakycat"} -> 201 {"id":34,"name":"flakycat"}

3) 해당 카테고리로 지출 생성
   POST /api/expenses (Bearer TOKEN) {"categoryId":34,"amount":1000,"content":"flakyexp","memo":""} -> 201

4) 회원 탈퇴 시도 (비밀번호 정확)
   DELETE /api/users/me (Bearer TOKEN) {"password":"qaPass123"}
   -> 401 Unauthorized (빈 바디) *** 클라이언트에 보이는 응답 ***
```

**서버 로그(server.log)에 남은 실제 원인:**

- 클라이언트는 401을 받으므로(DEF-004 참조) "인증 문제"로 오인하게 되어 실제 원인(계정 삭제 로직 결함)을 파악하기 매우 어려움
- 다만 트랜잭션 롤백 덕분에 데이터가 깨지지는 않음(불행 중 다행)

### 제안 수정
`Category`/`Expense` 매핑 재설계 필요. 예:
- `User.categories`, `User.expenses`의 cascade 순서/방식 재검토, 혹은
- `UserService.deleteAccount()`에서 명시적으로 `expenseRepository.deleteAllByUser(user)` → `categoryRepository.deleteAllByUser(user)` → `userRepository.delete(user)` 순서로 명시적 삭제, 혹은
- `Expense.category` FK에 `ON DELETE CASCADE` 적용 후 JPA에서도 그에 맞게 처리

## DEF-004 [Critical, 시스템 전역] GlobalExceptionHandler 미처리 예외가 클라이언트에는 401로 반환됨

### 현상
`GlobalExceptionHandler`가 명시적으로 처리하는 애플리케이션 커스텀 예외(DuplicateEmailException, CategoryNotFoundException 등)는 항상 올바른 상태코드(400/404/409 등)로 정상 응답되는 반면, **그 외의 모든 예외**(Spring 표준 예외인 `MissingServletRequestParameterException`, `MethodArgumentTypeMismatchException`, 매핑되지 않는 라우트의 404, DB 예외 등)는 **인증된 요청임에도 불구하고 클라이언트에는 401 Unauthorized(빈 바디)로 응답**된다. 이는 SecurityConfig에 등록된 `/error` 경로가 `permitAll` 목록에 없어, `sendError()`로 인한 내부 `/error` 포워딩이 다시 Spring Security 필터체인을 통과하면서 인증되지 않은 요청으로 처리되어 커스텀 `authenticationEntryPoint`(→401)가 실행되는 것으로 추정된다.

### 재현 절차 (실제 API 호출, 모두 유효한 인증 토큰 사용)
```
[재현 1] 필수 쿼리 파라미터 누락 (TC-063)
GET /api/expenses/summary?startDate=2020-01-01   (endDate 누락, Authorization: Bearer <유효토큰>)
-> 401 Unauthorized (빈 바디)
※ 서버 로그: "Resolved [MissingServletRequestParameterException: Required request parameter 'endDate' ... is not present]"
   -> Spring 내부적으로는 400으로 처리(Resolved)되었다고 로그에 남지만, 실제 클라이언트 응답은 401

[재현 2] 잘못된 타입의 경로변수
DELETE /api/categories/abc   (Authorization: Bearer <유효토큰>)
-> 401 Unauthorized (빈 바디)   (기대: 400 Bad Request)

[재현 3] 잘못된 형식의 JSON 바디
POST /api/categories  Body: "{invalid json"   (Authorization: Bearer <유효토큰>)
-> 401 Unauthorized (빈 바디)   (기대: 400 Bad Request)

[재현 4] 존재하지 않는 라우트
GET /api/nonexistent-route   (Authorization: Bearer <유효토큰>)
-> 401 Unauthorized (빈 바디)   (기대: 404 Not Found)

[비교] 실제 미인증 요청(정상적인 401 케이스)
GET /api/categories  (Authorization 헤더 없음)
-> 401 Unauthorized (빈 바디)   <- 위 4가지 재현과 응답이 구분 불가능할 정도로 동일함
```
4가지 재현 모두 **유효하고 만료되지 않은 실제 JWT 토큰**을 사용했음에도 401이 반환되어, "인증 실패"와 "요청 오류/서버 오류"를 클라이언트가 전혀 구분할 수 없는 상태임을 확인했다.

### 영향도
- **DEF-002, DEF-003도 이 결함의 영향을 받는다**: 두 결함의 진짜 원인(각각 500 매핑, DB 제약조건 위반)과 무관하게, 클라이언트가 최종적으로 받는 응답이 401로 오염되는 경우가 다수 확인됨
- 프론트엔드 `api.js`는 401을 받으면 **무조건 "로그인이 만료되었습니다"로 안내하고 강제 로그아웃/리다이렉트**를 수행하므로, 실제로는 로그인 상태가 정상이고 단순 입력 실수(날짜 파라미터 누락 등)나 서버측 버그(DEF-003)임에도 사용자에게는 "세션 만료"로 잘못 안내됨
- DEF-001(clearToken 미작동)과 결합되면, 사용자는 계속 "로그인이 만료되었다"는 안내를 반복해서 받으면서도 실제로는 토큰이 그대로 남아있어 문제 파악이 더욱 어려워짐
- 디버깅 관점에서도 API 오류 원인 파악이 크게 어려워지는 심각한 결함(서버 로그를 봐야만 진짜 원인을 알 수 있음)

### 제안 수정
1. `SecurityConfig`의 `permitAll` 목록에 `/error` 경로 추가, 또는
2. Spring Security의 `dispatcherTypes` 설정에서 `ERROR` 디스패치는 필터링하지 않도록 예외 처리
3. 근본적으로는 `GlobalExceptionHandler`에 `MissingServletRequestParameterException`, `MethodArgumentTypeMismatchException`, `HttpMessageNotReadableException`, `NoHandlerFoundException`, 포괄 `Exception` 핸들러를 추가하여 모든 예외가 `@RestControllerAdvice`를 통해 명시적으로 처리되도록 하는 것을 권장(이 경우 `/error` 포워딩 자체가 발생하지 않아 이번 결함을 근본적으로 회피할 수 있음)

## DEF-005 [Medium] 로그인 실패 횟수 제한(브루트포스 방어) 없음

### 현상
동일 계정에 대해 잘못된 비밀번호로 5회 연속 로그인 실패 후에도 지연이나 잠금 없이 즉시 정상 비밀번호로 로그인이 성공한다.

### 재현 절차
```
POST /api/users/login {"email":"qa_userA_...@test.local","password":"wrong1"} -> 401
POST /api/users/login {"email":"qa_userA_...@test.local","password":"wrong2"} -> 401
POST /api/users/login {"email":"qa_userA_...@test.local","password":"wrong3"} -> 401
POST /api/users/login {"email":"qa_userA_...@test.local","password":"wrong4"} -> 401
POST /api/users/login {"email":"qa_userA_...@test.local","password":"wrong5"} -> 401
POST /api/users/login {"email":"qa_userA_...@test.local","password":"qaPass123"} -> 200 (정상 로그인 즉시 성공)
```

### 영향도
무차별 대입 공격(Brute-force)에 취약할 수 있음. 다만 명시적 스펙에 반하는 "기능 결함"은 아니므로 보안 강화 권장 항목으로 Medium 등급 부여.

### 제안 수정
로그인 실패 횟수 기반 계정 잠금/지수 백오프, 또는 Rate limiting 도입 검토.

## DEF-006 [Low] Swagger UI/OpenAPI 문서가 인증 없이 노출됨

### 현상
`SecurityConfig`에서 `/swagger-ui/**`, `/v3/api-docs/**`가 `permitAll`로 설정되어 있어 인증 없이 API 명세 전체를 확인할 수 있다.

### 재현 절차
```
GET /swagger-ui/index.html  -> 200
GET /v3/api-docs             -> 200
```

### 영향도
개발/로컬 환경에서는 문제 없으나, 운영 배포 시 API 구조가 외부에 그대로 노출되어 공격 표면이 넓어질 수 있음.

### 제안 수정
운영 프로파일에서 `springdoc.api-docs.enabled=false`, `springdoc.swagger-ui.enabled=false` 설정 권장.

## DEF-007 [정보성, 버그 아님] README의 "전월 대비 증감률" 기능이 실제 API에 없음

### 현상
README에는 "전월 대비 증감률" 기능이 명시되어 있으나, 실제 `GET /api/expenses/summary` 응답에는 `totalAmount`, `categorySummaryList`만 존재하며 증감률 관련 필드가 전혀 없다.
```
GET /api/expenses/summary?startDate=2020-01-01&endDate=2030-12-31
-> {"totalAmount":20000.00,"categorySummaryList":[{"categoryName":"QA간식비","totalAmount":20000.00}]}
```

### 판단
코드(`ExpenseSummaryResponseDto`, `ExpenseService`)를 확인한 결과 관련 계산 로직 자체가 존재하지 않아, 결함이 아니라 **기획 문서와 실제 구현의 불일치(미구현 기능)**로 분류한다. 제품 책임자 확인 필요.
