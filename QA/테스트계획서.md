## 1. 문서 개요

### 1.1 목적
MoneyLog 프로젝트의 기획 스펙(README, 코드 기반 역추적)을 분석하여 테스트 범위와 검증 전략을 수립하고, 결함 발생 가능성이 높은 영역을 사전에 예측한다. 이 문서는 이후 STEP 2(TC 설계) ~ STEP 4(Sign-off)의 기준선이 된다.

### 1.2 참고 자료
- `README.md` (프로젝트 소개, 기술 스택, ERD, 주요 기능 목록)
- `MoneyLog/src/main/java/com/MoneyLog/**` 전체 소스 (Controller, Service, Repository, Entity, DTO, Exception, Security, Config)
- `MoneyLog/src/main/resources/**` (application.properties, static 프론트엔드 리소스)
- `MoneyLog/src/test/java/com/MoneyLog/**` 기존 통합 테스트 4종 (Auth, User, Category, Expense)
- 별도의 기획서/유저스토리 문서(PRD, Figma 등)는 리포지토리 내에서 발견되지 않음 → **본 문서의 기능 명세는 코드(Controller/Service/DTO/Exception) 및 README를 근거로 역추적한 것**임을 명시한다.

### 1.3 프로젝트 구조 관련 중요 확인 사항
- 최초 지시문에는 "프론트엔드가 별도 리포지토리일 수 있다"는 가정이 있었으나, 실제 탐색 결과 **프론트엔드는 별도 리포지토리가 아니라 이 Spring Boot 프로젝트 내부(`MoneyLog/src/main/resources/static/`)에 정적 HTML/CSS/JS 형태로 포함**되어 있다.
  - 페이지: `index.html`, `login.html`, `signup.html`, `dashboard.html`, `profile.html`
  - 스크립트: `js/api.js`(공통 fetch 래퍼), `js/auth.js`(토큰 저장/조회/삭제), `js/login.js`, `js/signup.js`, `js/dashboard.js`(지출/카테고리 CRUD, 도넛차트, 필터링), `js/profile.js`(프로필/비밀번호/탈퇴)
  - 즉, 이 프로젝트는 **모놀리식 구조(Spring Boot가 API + 정적 프론트엔드를 함께 서빙)**이며, iOS/Android 네이티브 앱은 코드베이스 내에 존재하지 않는다. 따라서 플랫폼 테스트 범위는 **Web(데스크톱 브라우저) 단일 플랫폼**으로 한정한다. (운영 규칙상 "해당 플랫폼이 존재하는 경우"에 해당하지 않는 iOS/Android는 테스트 범위에서 제외)
  - 프론트엔드 `BASE_URL`이 `http://localhost:8080`으로 하드코딩되어 있어, 로컬 구동 환경을 전제로 한다.

## 2. 기능 명세 역추적 (코드 기반)

### 2.1 도메인 및 ERD
README ERD 기준으로 User(사용자) 1:N Category(카테고리), User 1:N Expense(지출), Category 1:N Expense 관계이며, Category는 (사용자ID, 카테고리명) 복합 유니크 제약을 가진다.

### 2.2 API 인벤토리 (코드 기준)

| 기능 | Method | Endpoint | 인증 필요 | 비고 |
|---|---|---|---|---|
| 회원가입 | POST | /api/users/signup | 불필요 | 이메일 형식/필수, 비밀번호 8~20자 |
| 로그인 | POST | /api/users/login | 불필요 | JWT 발급 |
| 로그아웃 | POST | /api/users/logout | (인증 필터 통과 여부 불명확) | **TODO 상태, 서버측 로직 없음** |
| 사용자명 변경 | PUT | /api/users/me/username | 필요 | |
| 비밀번호 변경 | PUT | /api/users/me/password | 필요 | 현재 비밀번호 검증 |
| 회원 탈퇴 | DELETE | /api/users/me | 필요 | 비밀번호 검증, cascade 삭제(REMOVE) |
| 카테고리 생성 | POST | /api/categories | 필요 | 사용자별 이름 중복 불가 |
| 카테고리 목록 조회 | GET | /api/categories | 필요 | |
| 카테고리 수정 | PUT | /api/categories/{id} | 필요 | 소유권 검증, 이름 중복 검증 |
| 카테고리 삭제 | DELETE | /api/categories/{id} | 필요 | 소유권 검증, 지출 존재 시 삭제 불가 |
| 지출 생성 | POST | /api/expenses | 필요 | categoryId 소유권 검증 포함 |
| 지출 목록 조회 | GET | /api/expenses | 필요 | categoryId/startDate/endDate 선택적 필터 |
| 지출 수정 | PUT | /api/expenses/{id} | 필요 | 소유권 검증 |
| 지출 삭제 | DELETE | /api/expenses/{id} | 필요 | 소유권 검증 |
| 지출 요약(통계) | GET | /api/expenses/summary | 필요 | startDate/endDate 필수, 총액+카테고리별 합계 |

주의: README에는 "전월 대비 증감률" 기능이 명시되어 있으나, `ExpenseSummaryResponseDto`/`ExpenseService`에는 총액과 카테고리별 합계만 존재하고 전월 대비 증감률 계산 로직이 코드상 확인되지 않는다. **기획-구현 불일치 가능성**으로 STEP 3에서 실제 화면/응답을 재확인하고, 미구현이면 결함이 아닌 "기획 대비 미구현 기능"으로 별도 분류한다.

### 2.3 인증/인가 구조
- JWT 기반 Stateless 인증(`JwtAuthenticationFilter` + `JwtTokenProvider`), 토큰의 subject=userId, claim=role.
- `SecurityConfig`에서 `/api/users/signup`, `/api/users/login`, swagger 경로, 정적 리소스, `/login`, `/signup`, `/dashboard` 뷰 경로는 인증 없이 허용, 그 외 전체 `anyRequest().authenticated()`.
- 인증 실패 시 `AuthenticationEntryPoint`가 단순 `sendError(401)` 처리(본문 없음, 프론트 `api.js`는 401을 감지해 강제 로그아웃 처리).
- 리소스 소유권 검증은 Service 계층에서 `userId` 비교로 수행(Category/Expense 각각 `AccessDeniedException` → 403).

## 3. 기존 자동화 테스트 커버리지 분석

기존 통합 테스트(`AuthIntegrationTest`, `UserIntegrationTest`, `CategoryIntegrationTest`, `ExpenseIntegrationTest`, 총 8개 이상 테스트 메서드)를 검토한 결과는 다음과 같다.

### 3.1 커버된 영역
- 회원가입 → 로그인 → 보호된 API 접근 정상 흐름, 토큰 없이 401
- 사용자명 변경 성공
- 비밀번호 변경 성공/실패(현재 비밀번호 불일치)
- 회원 탈퇴 성공(탈퇴 후 재로그인 401) / 탈퇴 시 비밀번호 불일치 400
- 카테고리 생성/목록조회/삭제/수정 성공, 다른 사용자 카테고리 삭제 시 403, 자기 자신과 동일 이름으로 수정(허용), 타 카테고리와 이름 중복 시 수정 실패
- 지출 생성/목록조회/삭제/수정 성공, 다른 사용자 지출 삭제 시 403, 카테고리 변경 포함 수정, category 필터 동작, 지출 요약 조회 성공

### 3.2 자동화 테스트에서 확인되지 않은 영역 (Gap)
- **카테고리 생성 시 이름 중복(DuplicateCategoryException, 409)** — 현재는 "수정" 시나리오만 커버, "생성" 시나리오 미커버
- **카테고리 삭제 시 소속 지출이 존재하는 경우 삭제 거부(CategoryHasExpensesException, 409)** — 전혀 커버되지 않음
- **지출 입력값 검증 실패**: 금액 0/음수, 금액 null, content 공백, categoryId null → 400 응답 여부 미검증
- **지출 생성/수정 시 타 사용자 소유 categoryId 사용** → CategoryAccessDeniedException(403) 발생 여부 미검증 (로직상 존재하나 테스트 없음)
- **지출 요약(summary) API의 필수 파라미터 누락**(startDate/endDate 없음) 시 400 여부, **startDate > endDate**(역전) 케이스, 빈 기간(지출 없음)일 때 totalAmount 처리(0 반환 로직은 있으나 테스트 없음)
- **회원 탈퇴 시 연쇄 삭제(Cascade)의 DB 레벨 검증** — 현재는 "재로그인 실패"만 확인, 실제 Category/Expense 레코드가 삭제되는지(고아 레코드 방지)는 미검증
- **JWT 관련 예외 케이스**: 만료된 토큰, 위조/변조된 토큰, 형식이 잘못된 Authorization 헤더(Bearer 접두어 누락 등) → 현재는 "토큰 없음" 케이스만 커버
- **회원가입 검증 실패 케이스**: 이메일 형식 오류, 이메일 누락, 비밀번호 길이 미달/초과, 이메일 중복(DuplicateEmailException, 409) — 코드상 로직은 있으나 통합 테스트 없음
- **로그인 실패(존재하지 않는 이메일/틀린 비밀번호)** — InvalidCredentialsException 401 케이스 명시적 테스트 없음
- **UserNotFoundException이 500으로 처리되는 경로**(탈퇴 후에도 유효한 토큰으로 API 재호출) 미검증
- **Role/권한(ADMIN vs USER) 분기 로직** — Role enum은 존재하나 ADMIN 전용 기능/엔드포인트가 코드상 없어 실질적으로 미사용 상태로 보임(설계 의도 확인 필요)

## 4. 예측 결함 영역 (Risk-based, 우선순위 순)

### 4.1 🔴 Critical 후보

**(1) 프론트엔드 토큰 삭제 로직 오류 (localStorage 키 오타)**
`static/js/auth.js`의 `clearToken()` 함수가 다음과 같이 구현되어 있다.
```js
function clearToken(){
    localStorage.removeItem("toekn");   // 오타: "token"이 아닌 "toekn"
}
```
반면 저장/조회 함수는 정상적으로 `"token"` 키를 사용한다(`saveToken`, `getToken`). 이로 인해:
- 세션 만료(401) 시 `api.js`가 `clearToken()`을 호출해도 실제 토큰은 삭제되지 않아 `isLoggedIn()`이 계속 `true`를 반환 → 로그인 페이지로 강제 이동은 되지만 새로고침 시 다시 대시보드로 진입 가능하거나 만료 알림이 반복될 가능성.
- **회원 탈퇴 시(`profile.js`)** `clearToken()` 후 `/`로 리다이렉트하지만 실제로는 토큰이 브라우저에 남아있음. 탈퇴한 계정의 JWT는 만료 전(기본 1시간)까지 유효한 서명을 가지므로, 이후 보호된 API 호출 시 (2)번 항목과 결합되어 심각한 오류로 이어질 수 있음.
- 공용 PC/브라우저에서 로그아웃 후에도 민감한 토큰이 잔존하는 **보안 이슈**로 이어질 수 있음.
→ STEP 3에서 실제 브라우저(DevTools localStorage)로 재현 검증 필요.

**(2) UserNotFoundException → 500 매핑 (탈퇴 계정의 잔존 토큰 사용 시나리오와 결합)**
`GlobalExceptionHandler`에서 다른 NotFound 계열(Category/Expense)은 404로 매핑되나 `UserNotFoundException`만 500(Internal Server Error)으로 매핑되어 있다. 회원 탈퇴 후 (1)번의 잔존 토큰 문제와 결합하면, 탈퇴한 사용자가 만료 전 토큰으로 API를 계속 호출할 경우 401/404가 아닌 500 오류가 노출되어 사용자 경험 저하 및 서버 오류 로그 오염 가능성이 있다.

**(3) 인증/인가 우회 및 소유권 검증**
- 타 사용자 소유 Category/Expense에 대한 CRUD 시도 시 403이 정상 반환되는지(특히 지출 생성/수정 시 categoryId가 "존재하지만 타인 소유"인 경우) 실제 구동 환경에서 재검증 필요. 코드상 `getCategoryByIdAndUser`를 경유하므로 로직은 타당하나, 자동화 테스트 커버리지가 낮아 회귀 위험이 있음.
- JWT 위조/변조/만료 토큰 처리가 실제로 401을 반환하는지, 만료 임박 토큰 갱신 전략 부재 여부.

### 4.2 🟠 High 후보
- 카테고리 삭제 시 소속 지출 존재 여부 검증(CategoryHasExpensesException) — 자동화 테스트가 전무하여 회귀 시 조용히 깨질 위험이 가장 큼.
- 프론트-백엔드 데이터 타입 불일치: `dashboard.js`에서 `categoryId`를 `<select>`의 문자열 값으로 전송(JSON.stringify 시 문자열), 백엔드는 `Long categoryId` 기대 — Jackson 역직렬화 관용성(coercion) 정책에 따라 400 오류가 발생할 수 있음. 실제 폼 제출 E2E로 검증 필요.
- `AuthDto.Request`(로그인 요청 DTO)에 `@NotBlank`/`@Email` 등 Bean Validation이 전혀 없음 — 이메일/비밀번호 공백 요청 시 검증 계층을 우회하고 서비스 로직까지 도달, 에러 메시지 일관성 부족 가능.
- GlobalExceptionHandler에 `MethodArgumentTypeMismatchException`(예: `categoryId=abc` 같은 잘못된 타입의 쿼리 파라미터), `HttpMessageNotReadableException`(잘못된 JSON), 포괄 `Exception` 핸들러가 없어 스택트레이스가 노출되거나 예기치 않은 500이 발생할 가능성.
- 통계(summary) API의 날짜 파라미터 필수 여부/역전 케이스 미검증 — 잘못된 날짜 조합 시 서버 오류 또는 잘못된 집계 가능성.

### 4.3 🟡 Medium 후보
- 로그아웃 API가 서버측에서 아무 동작도 하지 않음(TODO) — 토큰 무효화(블랙리스트) 메커니즘 부재로, 로그아웃해도 탈취된 토큰은 만료 전까지 유효. 기능 명세상 의도된 설계일 수 있으나 리스크로 기록.
- 로그인 시도 횟수 제한(rate limiting)/계정 잠금 없음 — 무차별 대입 공격에 취약할 수 있음.
- 회원가입 시 `userName` 길이/특수문자 제한 없음(공백만 아니면 통과), 이메일 대소문자 중복 처리 정책 불명확(`existsByEmail`이 대소문자를 구분하는지).
- 지출 메모(`memo`) 필드는 필수 검증이 없어 매우 긴 문자열 입력 시 DB 컬럼 길이 제약 초과 가능성(엔티티에 `@Column` 길이 제한 미지정, DB 기본값에 의존).
- CORS 허용 Origin이 `localhost:8080`, `127.0.0.1:5500`으로 하드코딩 — 배포 환경(다른 도메인/포트) 전환 시 CORS 오류 발생 가능성. 로컬 QA에서는 큰 문제 아니지만 확인 필요.
- `DeleteAccountRequestDto`(미사용으로 보이는 dead code)와 `UserDto.DeleteAccountRequest`가 중복 존재 — 기능에는 영향 없으나 유지보수 리스크.

### 4.4 🟢 Low 후보
- 에러 메시지/한글 문구의 톤앤매너 일관성(공백 처리 등 사소한 오탈자 가능성 — 코드 내 "excetion" 등 변수명 오탈자 발견, 기능 영향 없음)
- 프론트엔드 UI의 로딩 상태 표시 부재(요청 중 스피너 없음), 통계 카드의 숫자 포맷팅(₩ 표기, 소수점) 일관성

## 5. 테스트 범위 및 전략

### 5.1 테스트 레벨 및 담당 도구
| 레벨 | 대상 | 방법 | 비고 |
|---|---|---|---|
| API 통합 테스트(회귀) | 인증, User, Category, Expense CRUD, 요약 API의 정상/예외 흐름 | 기존 MockMvc 통합 테스트 확장 실행 + 수동 API 호출(Swagger UI / curl / Postman) | Gap으로 식별된 케이스(4.1~4.3) 위주로 수동 검증 후 결함 리포트, 필요 시 자동화 테스트 보강은 개발자 영역이므로 QA는 결함으로만 리포팅 |
| E2E(브라우저) | 회원가입~로그인~대시보드~카테고리/지출 CRUD~프로필~탈퇴 전 과정 | 실제 브라우저(Chrome 등) + DevTools(Network/LocalStorage) 수동 조작 | localStorage 토큰 이슈, CORS, 폼 검증 메시지 노출 등은 E2E에서만 발견 가능 |
| 보안/인가 | JWT 위변조, 만료, 타 사용자 리소스 접근 | 수동 API 호출(토큰 변조, 다중 계정 준비) | Critical 등급 우선 검증 |
| 데이터 정합성 | 회원 탈퇴 cascade, 카테고리-지출 소유권, 통계 합계 정확성 | DB 직접 조회(MySQL) 또는 API 재조회로 간접 검증 | |

### 5.2 API 레벨로 충분히 커버 가능한 범위
- CRUD 정상/예외(404/403/409/400) 응답 코드 및 메시지 검증
- Bean Validation 동작(필수값, 형식, 범위)
- 소유권 검증(타 사용자 리소스 접근 차단)
- 필터/검색 파라미터 조합(categoryId, startDate, endDate)

### 5.3 실 구동 후 수동/E2E 확인이 반드시 필요한 범위
- **localStorage 토큰 저장/삭제 동작(4.1-(1) 재현)** — API 레벨에서는 발견 불가, 브라우저 DevTools 필수
- 도넛 차트(Chart.js) 렌더링 정확성(카테고리별 비율/색상/범례)
- 필터 폼 → 목록/차트 갱신 연동, 지출 등록/수정 모달의 카테고리 select 동기화
- 401 발생 시 프론트엔드의 강제 로그아웃/리다이렉트 UX
- 프로필 페이지의 사용자명/비밀번호 변경/탈퇴 폼과 에러 메시지 노출
- 새로고침, 뒤로가기, 다중 탭 등 브라우저 상태 관련 시나리오

### 5.4 플랫폼 범위
- **Web(데스크톱 브라우저)만 해당**. iOS/Android 네이티브 앱은 리포지토리에 존재하지 않아 테스트 범위에서 제외한다. 프론트엔드가 정적 리소스로 백엔드와 함께 서빙되므로 별도 프론트 리포지토리/배포 파이프라인 없음.
- 반응형/모바일 브라우저 대응 여부는 STEP 3에서 화면 확인 후 필요 시 리스크로 별도 기록(현재 CSS 구조상 모바일 대응 여부 불명확).

### 5.5 실행 순서 원칙(STEP 3 대비)
1. Critical 후보(4.1)부터 우선 실행 — 특히 토큰 삭제 오류(4.1-(1))와 UserNotFoundException 500 매핑(4.1-(2))의 결합 시나리오
2. High 후보(4.2) — 자동화 Gap 영역(카테고리 삭제 제약, 데이터 타입 불일치, 로그인 DTO 검증 부재)
3. Medium/Low는 Critical/High 확인 후 순차 진행

### 5.6 테스트 환경
- 로컬 구동: `MoneyLog/gradlew.bat bootRun` (또는 IDE 실행), MySQL 8.0.25 로컬 인스턴스 필요(`application-DB.properties`, `application-secret.properties`는 Git에 포함되지 않는 것으로 확인됨 → 로컬 환경 구성 필요)
- 브라우저: 최신 Chrome 기준(추가로 Edge 등 크로스브라우저는 시간 허용 시)
- API 테스트 도구: Swagger UI(`/swagger-ui.html`, 인증 없이 접근 가능하도록 설정되어 있음 — 운영 환경 노출 여부도 리스크로 기록), curl/Postman
- 다중 계정 준비: 소유권 검증 테스트를 위해 최소 2개 이상의 사용자 계정 필요

## 6. 리스크 및 가정/제약사항
- 기획서/유저스토리 원문이 없어 일부 기능(예: README의 "전월 대비 증감률")은 실제 의도와 다르게 해석되었을 수 있다. STEP 3 수행 중 실물 확인 후 재분류한다.
- `application-secret.properties`(JWT 시크릿 등)가 리포지토리에 없어 로컬 환경 구성이 QA 착수의 선행 조건이다. 환경 미구성 시 STEP 3 착수가 지연될 수 있다.
- 프론트엔드가 순수 정적 리소스(프레임워크 없는 vanilla JS)이므로 크로스 브라우저 이슈나 상태 관리 버그(위 4.1-(1) 등)가 API 테스트만으로는 드러나지 않아 E2E 비중을 높게 잡는다.
- ADMIN 역할(Role.ADMIN)에 대응하는 기능이 코드상 확인되지 않아, 관리자 기능은 이번 QA 범위에서 제외하거나 "미구현"으로 별도 기록한다.
